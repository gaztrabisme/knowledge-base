A knowledge base (KB) stores searchable passages. An embedding is a numeric representation of text; its dimension is its number of coordinates. A dense embedding has a value at every coordinate; a sparse representation records selected terms and weights. BM25 is the keyword-ranking formula used here. Hybrid search combines dense and keyword candidates. A cross-encoder reads a query and a candidate passage together to judge relevance, making reranking more expensive than comparing precomputed vectors. MCP, the Model Context Protocol, exposes the search tools to coding agents. [KB architecture](/Users/GaryT/Documents/Work/tools/knowledge-base/CLAUDE.md:31).

Existing skip logic prevents some repeated work but is not reliable content-version tracking. A content hash is a fingerprint calculated from an artifact's bytes. ## Techniques

“Fit” means suitable for the recommended direction, subject to validation; “maybe” means a gated experiment; “no” means unsuitable as the default replacement. Published speed and compression figures apply to the source's experiment or representation. “Not found” means no applicable numerical gain was published in the cited material.

Quantization approximates numbers using fewer bits. Float32 uses 32-bit floating-point numbers; int8 and int4 use 8-bit and 4-bit integers. Model-weight quantization changes neural inference, while stored-vector quantization changes similarity search. A transformer is a neural network that accounts for surrounding text; its forward pass computes its output. Distillation transfers a larger model's behavior into a smaller model. Pooling combines token representations into one passage representation. MTEB is the Massive Text Embedding Benchmark; its public scores are not this KB's scores. [Quantization definitions](https://onnxruntime.ai/docs/performance/model-optimizations/quantization.html), [distillation and benchmark context](https://huggingface.co/blog/ettin-reranker).

## Recommended stack

**1. Make reuse correct before accelerating computation.** Maintain a manifest for each source containing its content hash, parser version, chunking rules, heading policy and expected child count. Keep parse, chunk and embedding artifacts separately reusable. A parser change invalidates parsing downstream; an embedding-model change invalidates embeddings but need not reparse unchanged source files. Require complete indexed counts before marking a source finished, and remove obsolete child identifiers when replacing it. This is a proposed design, based on hash-aware ingestion patterns rather than a request to install another framework. [Ingestion pattern](https://developers.llamaindex.ai/python/framework/module_guides/loading/ingestion_pipeline/).

Cache exact embedding inputs, including their heading and document title, so duplicates can reuse computation while retaining distinct citations and source locations. Do not collapse separate editions or code versions merely because their prose is similar. Semantic deduplication is an optional audit step, not an automatic deletion policy. **Inference:** unchanged ingestion can perform zero parsing and zero embedding after validation; the resulting savings depend on how much of each intake is unchanged, which is currently **not found**.

Keep the native PDF path and its quality fallback. Reuse a TextPage only where extraction repeats. For courses, store transcript segments and selected informative frames with timestamps and source identity; hash each artifact independently. Avoid indexing every repeated slide as a new semantic passage. This frame-selection policy is a proposed design whose effect on visual-answer recall must be measured. It is not an asserted result from this book-only test set.

**2. Use a CPU-conscious model adapter, conditional on the model decision.** If the other unit approves EmbeddingGemma 2, load only its text components for online text queries. Image/audio components can be used during offline indexing when the corresponding content requires them. Start from a float32 reference; test ONNX float32, then dynamic int8, with OpenVINO as a competing CPU runtime. Int4 is a later experiment, not an assumed free improvement.

The current adapter recognizes the older embeddinggemma-300m identifier, not the new model. Its unknown-model default uses 1,024 dimensions and a Jina task convention. A model-name environment change alone would therefore be unsafe. Register the new output size and exact query/document formatting explicitly. Google requires float32 or supported bfloat16, a 16-bit format with a wider numeric range than float16; float16 can produce invalid or silently degraded embeddings. Preserve model-specific pooling, learned projections and normalization in any export. [Current adapter](/Users/GaryT/Documents/Work/tools/knowledge-base/knowledge_base/embedder.py), [Gemma 2 usage and precision](https://huggingface.co/google/embeddinggemma-2).

Test 256-coordinate Matryoshka output first, with 512 as a fallback and 768 as the reference. Normalize after truncation and keep query/document dimensions identical. **Inference:** truncating the output reduces stored-vector arithmetic and bytes; it does not remove the model's transformer computation. For code repositories, verify code-search prompt behavior separately rather than applying a code prompt to every book.

**3. Keep Qdrant and BM25; start with scalar compression and rescoring.** Store original vectors for rescoring, and use an int8 search representation. Keep the compressed representation and, if the memory budget permits, the HNSW graph resident; move large originals and payloads to disk only after measuring cold behavior. A float rescore recomputes similarity from the original vector; it is separate from the subsequent neural reranker. Oversampling means retrieving additional compressed candidates to compensate for approximation errors.

Inspect the installed Qdrant version before writing configuration. Version 1.19 introduces component memory tiers: pinned stays resident, cached warms an evictable disk cache, and cold loads lazily. Older on_disk and always_ram flags still work but are deprecated. Do not paste new configuration into an unidentified older server. [Memory-tier release](https://qdrant.tech/blog/qdrant-1.19.x/).

Index actual book and domain filter fields and record graph settings. The graph's m controls connectivity; ef_construct controls construction effort; hnsw_ef controls query search effort. Raising them can cost memory, indexing time or query time. A rescore-only full-size vector can omit its HNSW graph, as Qdrant documents with m=0, if an eventual two-vector design passes testing. Do not retain two graph indexes merely because two vector sizes are available. [Hybrid multi-stage patterns](https://qdrant.tech/documentation/search/hybrid-queries/).

Keep scalar quantization as the initial choice. Binary, product and TurboQuant are secondary experiments only if memory remains limiting. The compressed byte count does not include retained originals, HNSW or BM25. In particular, Turbo4 removes original-vector rescoring and is not the initial recommendation.

**4. Preserve the current retrieval ordering while reducing inference overhead.** Keep the original-query dense and BM25 legs, DBSF and 50 fused candidates as the control. Optimize the current Ettin-150M runtime before changing its model. The May 2026 ONNX deferral cited an incompatible dependency stack. Current Optimum ONNX documentation lists ModernBert, which is new evidence supporting a fresh export check, but not proof that every module of Ettin's custom scoring head exports correctly. Its pooling, dense layers and normalization must all be retained. [Old deferral](/Users/GaryT/Documents/Work/tools/knowledge-base/wiki/decisions.md:149), [current supported architectures](https://huggingface.co/docs/optimum-onnx/onnx/overview).

Then compare Ettin-68M with the same 50 candidates and the same inputs. Next test reranking 30 rather than 50 candidates as a separate experiment. **Calculated inference:** that scores 40% fewer pairs; neither latency nor retrieval quality necessarily changes by 40%. Recalibrate the score floor for any new model or quantized scoring distribution on a separate calibration split. Do not transplant the value 4 automatically to a different model, and do not tune it on the final hard-set answers.

Use bounded exact query-result and query-embedding caches. A result key must include the exact query, any keyword override or query variants, filters, top-k, output detail, collection generation, embedding revision and reranker/cutoff policy. Resolve the collection generation rather than caching forever under the alias name. Cache hits and misses must be measured separately. Avoid approximate “semantic” result reuse for precise identifiers or book citations. Python's cache documentation also notes that concurrent misses can execute the underlying operation more than once; use request coalescing if repeated simultaneous queries are observed. [Cache behavior](https://docs.python.org/3/library/functools.html).

Fetch child text and the metadata needed for reranking at the candidate stage, then obtain full parents only for final results requesting them. **Inference from search.py:** this avoids unnecessary parent-text transfer for rejected candidates; actual byte and latency savings are **not found**. Retain the existing brief tool response, rather than undoing an already measured context-cost reduction. Shared parent storage is optional after this simpler payload-fetch change.

For CPU execution, tune batch size, input-length grouping and per-model thread count together with concurrency. A throughput-optimal batch can delay an individual agent query; an unbounded thread pool per MCP process can make simultaneous clients slower. Keep model instances long-lived and establish whether multiple agent processes duplicate their weights before introducing a shared inference service. [Thread controls](https://onnxruntime.ai/docs/performance/tune-performance/threading.html).

**Expected end-to-end effect.** A defensible total speedup is **not found**: the current stage shares and cache hit rates are missing. Do not multiply Model2Vec's 500×, binary search's 40× and scalar search's 2× claims; they affect different work and come from different experiments.

There is a precise capacity scenario. At the current point count, 256-coordinate float32 Gemma 2 originals occupy **293,604,352 bytes**, and their int8 copies occupy **73,401,088 bytes**. Keeping both occupies **367,005,440 bytes**, compared with the current calculated 1,024-coordinate float32 array's 1,174,417,408 bytes: **3.2× fewer representation bytes**, excluding every index and payload. The resident compressed array alone is **16× smaller** than that current dense-array baseline. These are arithmetic projections, not observed total RAM/disk savings. Retaining an additional 768-coordinate original would substantially change the total; the table's compression factors cannot be stacked without counting all copies.

For latency, use the measured stage times in the formula: new time = unchanged work + embedding time/embedding acceleration + search time/search acceleration + reranking time/reranking acceleration. Add actual cache-hit frequencies. **Illustrative inference, not a forecast:** accelerating a component that occupies 75% of runtime by 2× produces a total 1.6× speedup. The recommended combination should reduce reprocessing and dense storage; its CPU latency benefit remains an empirical question.
